## 1. Project Overview & Non-Goals

### Vision
Una PWA para un emprendimiento de dos personas que vende gorritos y colitas de satén para el pelo.
Reemplaza el control manual en Google Sheets por una app instalable en el celular: registrar una
venta descuenta el stock al instante, cada gasto de tela o mano de obra queda anotado, y el
dashboard muestra de un vistazo cuánto se vendió, cuánto se invirtió y cuánto queda de ganancia.
Google Sheets sigue siendo la única base de datos — la app lee y escribe la misma planilla que las
dos dueñas pueden seguir abriendo a mano. Si esto no existe, vuelven a lo que tenían: anotar ventas
y stock a mano en la planilla, sin descuento automático y sin forma rápida de mandarle al cliente el
detalle de su compra.

### Users
| Persona | What they come to do | Frequency |
|---|---|---|
| Dueña / socia (2 personas, mismo acceso) | Registrar una venta, anotar un gasto de tela o mano de obra, revisar stock y ganancia | Varias veces al día |

### Goals — v1 scope
1. Registrar una venta (producto + color + cantidad + cliente opcional) descuenta el stock del
   producto correspondiente, en la misma planilla de Google Sheets.
2. Compartir el detalle de una venta (artículo + precio) con el cliente por WhatsApp en un toque.
3. Anotar gastos de tela, mano de obra u otro, y ver cuánto se invirtió en un período.
4. Ver un dashboard con ventas del período, inversión, ganancia y productos con poco stock.
5. Administrar el catálogo de productos (tipo, color, precio, costo) — extensible a nuevos tipos
   además de gorritos y colitas.
6. Funcionar como app instalable en el celular (PWA), utilizable fuera de casa.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| Pagos en línea / checkout para clientes | Las ventas se cobran en persona o por transferencia fuera de la app; no es una tienda | Si empiezan a vender también online, sin contacto directo con el cliente |
| Cuentas de usuario individuales / roles distintos | Las dos socias hacen exactamente lo mismo; una identidad compartida (PIN) alcanza | Si suman una tercera persona con acceso más limitado |
| Alertas push automáticas de stock bajo | El dashboard ya muestra stock bajo al abrir la app; una notificación push agrega complejidad (service worker push, permisos) sin pedido explícito | Si el volumen crece tanto que no abren la app seguido |
| Multi-negocio / multi-tenant | Es una sola marca, un solo Sheet | Si el negocio se convierte en franquicia o suman otra línea de productos totalmente separada |
| Reportes avanzados / export a PDF | El propio Google Sheet ya sirve como reporte exportable | Si piden un resumen mensual formateado para mostrar a terceros (ej. un contador) |
| Migrar de Google Sheets a una base de datos real | A este volumen (bajo tráfico, 2 usuarias) Sheets alcanza; ver §20.2 Riesgos | Si el volumen de ventas/día crece un orden de magnitud, o si se suma un tercer usuario editando simultáneamente seguido |
| Modo oscuro | No fue pedido; el foco es que ande bien en celular con luz de día en el taller | Si se pide explícitamente |
| Traducción / multi-idioma | La app es para uso interno en español | No aplica — es una herramienta interna, no un producto que se vende |

**The builder must not implement anything in this table**, even if it seems like a small addition
while working on an adjacent step.

### Success metrics
| Metric | Target | How measured |
|---|---|---|
| Registrar una venta completa (abrir app → guardada) | Bajo 30 segundos en un celular real | Cronómetro manual la primera semana de uso real |
| Ninguna venta pierde datos o descuenta stock dos veces | 0 incidentes en el primer mes | Revisión manual de la pestaña "Ventas" vs. "Productos" |
| App instalada en los celulares de las dos socias | Ambas la usan sin abrir el navegador | Confirmación directa con las usuarias |

## 2. Tech Stack

**Runtime track: TypeScript/Node.js.** Un solo lenguaje, deploy en minutos, y el ecosistema de React
es el que mejor sirve una UI mobile-first con formularios (`knowledge/runtime-tracks/ts-node.md`).

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime | TypeScript 7.0.2 sobre Node.js 24.19.0 LTS | Un lenguaje en todo el stack; LTS activo, no la línea Current |
| Framework | Next.js 16.3.0 (App Router, Server Actions) | Formularios con Server Actions evitan escribir una capa de API REST completa que nadie más consume — menos superficie para 2 usuarias, contra un backend Express separado |
| Styling | Tailwind CSS 4.3.3 | Config CSS-first, rápido de armar tablas/formularios densos, mobile-first por defecto |
| Component layer | Componentes propios (sin librería de UI) | El catálogo de pantallas es chico (login, dashboard, 3 listas, 3 formularios); una librería como shadcn agrega peso de instalación que no se paga a este tamaño |
| Database | **Google Sheets** (API v4, vía `googleapis`) — decisión explícita del usuario, no el default de este framework | El pedido fue explícito: mantener todo visible/editable en la planilla, sin duplicar información. Contra Postgres (el default de `knowledge/capabilities/database.md`): a este volumen (2 usuarias, bajo tráfico) el riesgo de Sheets es aceptable — ver §20.2 |
| ORM / data access | Interfaz propia `DataRepo`, con dos implementaciones: `MemoryRepo` (fake, dev/tests) y `GoogleSheetsRepo` (real) | No hay ORM porque no hay base relacional; la interfaz es lo que permite probar y correr la app sin credenciales de Google desde el primer minuto |
| Auth | PIN compartido + cookie firmada (`jose`, JWT HS256) | Dos usuarias, mismo acceso, sin necesidad de cuentas — decisión explícita del usuario tras evaluar el riesgo de dejar la app completamente abierta |
| Background work | Ninguno | No hay colas ni jobs — todas las escrituras son síncronas y rápidas (una fila en un Sheet) |
| Payments | NOT APPLICABLE | Non-Goal — ver §1 |
| File storage | Ninguno | No hay subida de imágenes/archivos en v1 |
| Email / notificaciones | Ninguno (compartir es por WhatsApp, iniciado por la usuaria) | Non-Goal — ver §1 |
| Hosting | Vercel, conectado al repo de GitHub del usuario | Deploy automático en cada push, capa gratuita alcanza sobra para este tráfico, cero configuración de servidor |
| Package manager | pnpm 11.20.0 | Instalación estricta, evita dependencias fantasma |

### Compatibility check
Checked against `knowledge/stack-compatibility.md` — no known-bad combinations. Next.js 16.3.0
requiere Node `>=20.9.0` (cumplido por 24.19.0 LTS) y React `^19.0.0` (cumplido por React 19.2.8,
verificado en el `peerDependencies` publicado de `next@16.3.0`). `@ducanh2912/next-pwa@10.2.9`
declara `next: ">=14.0.0"` como peer, compatible con 16.3.0.

## 4. Data Model

Las tres entidades viven en tres pestañas de un mismo Google Sheet. No hay claves foráneas reales
— `GoogleSheetsRepo` las resuelve en memoria al leer el rango completo de cada pestaña (a este
volumen, unas pocas decenas de filas, es instantáneo).

### Entities

**Producto** — un artículo del catálogo (tipo + color es la variante).

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | string (uuid) | PK | Generado por el repo con `crypto.randomUUID()` |
| `tipo` | string | uno de `gorrito`, `colita`, o el que se agregue en `schemas.ts` | Extensible — ver `.claude/skills/agregar-recurso-sheets` |
| `color` | string | no vacío | Texto libre, ej. "rosa", "negro" |
| `precio_venta_centavos` | integer | >= 0 | Precio de venta actual, en centavos |
| `costo_tela_centavos` | integer | >= 0 | Costo de tela estimado por unidad |
| `costo_mano_obra_centavos` | integer | >= 0 | Costo de mano de obra estimado por unidad |
| `stock_actual` | integer | >= 0 | Nunca negativo — ver §4 Stock |
| `activo` | boolean | default `true` | Soft delete: `false` = no aparece en los selectores de venta |
| `creado_en` | string (ISO 8601 UTC) | not null | |

**Venta** — un evento de venta. Nunca se edita ni se borra (es un libro de ventas).

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | string (uuid) | PK | |
| `fecha` | string (`YYYY-MM-DD`) | not null | Fecha de la venta, zona horaria local del server |
| `producto_id` | string (uuid) | FK → Producto.id | |
| `producto_tipo` | string | not null | Copiado de Producto al momento de la venta (denormalizado, para leer el Sheet a simple vista) |
| `producto_color` | string | not null | Copiado de Producto al momento de la venta |
| `cantidad` | integer | > 0 | |
| `precio_unitario_centavos` | integer | >= 0 | Snapshot del precio al momento de vender — si el precio del producto cambia después, esta venta no cambia |
| `total_centavos` | integer | = `cantidad * precio_unitario_centavos` | Calculado, nunca editado a mano |
| `cliente_nombre` | string | opcional, default `""` | |
| `cliente_telefono` | string | opcional, default `""` | Si está, el link de WhatsApp abre directo con ese contacto |
| `creado_en` | string (ISO 8601 UTC) | not null | |

**Gasto** — un evento de inversión (tela, mano de obra, u otro). Ledger, igual que Venta.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | string (uuid) | PK | |
| `fecha` | string (`YYYY-MM-DD`) | not null | |
| `categoria` | string | uno de `tela`, `mano_obra`, `otro` | |
| `descripcion` | string | no vacío | Ej. "3m de satén rosa" |
| `monto_centavos` | integer | > 0 | |
| `creado_en` | string (ISO 8601 UTC) | not null | |

### Relationships
`Venta.producto_id` —(muchos a uno)→ `Producto.id`. No hay cascada de borrado: `Producto` nunca se
borra de verdad (soft delete vía `activo`), así que ninguna `Venta` queda huérfana.

### Indexes
NOT APPLICABLE — Google Sheets no tiene índices; `GoogleSheetsRepo` lee el rango completo de cada
pestaña y filtra en memoria. A la escala de este proyecto (decenas de filas por mes) esto es
instantáneo; ver §20.2 para el techo de este enfoque.

### Schema

Cada pestaña del Sheet tiene una fila de encabezado con estos nombres de columna, en este orden
exacto — `GoogleSheetsRepo` depende de este orden, no de los nombres (lee por posición de columna):

```
Productos!A1:H1  → id | tipo | color | precio_venta_centavos | costo_tela_centavos | costo_mano_obra_centavos | stock_actual | activo | creado_en
Ventas!A1:J1     → id | fecha | producto_id | producto_tipo | producto_color | cantidad | precio_unitario_centavos | total_centavos | cliente_nombre | cliente_telefono | creado_en
Gastos!A1:F1     → id | fecha | categoria | descripcion | monto_centavos | creado_en
```

Los esquemas de validación viven en `src/lib/data/schemas.ts` (Zod). Cuerpo completo, autoría del
paso 2:

```typescript
import { z } from "zod";

export const TIPOS_PRODUCTO = ["gorrito", "colita"] as const;
export const CATEGORIAS_GASTO = ["tela", "mano_obra", "otro"] as const;
export const UMBRAL_STOCK_BAJO = 3;

export const ProductoSchema = z.object({
  id: z.string().uuid(),
  tipo: z.enum(TIPOS_PRODUCTO),
  color: z.string().trim().min(1, "El color es obligatorio"),
  precio_venta_centavos: z.number().int().nonnegative(),
  costo_tela_centavos: z.number().int().nonnegative(),
  costo_mano_obra_centavos: z.number().int().nonnegative(),
  stock_actual: z.number().int().nonnegative(),
  activo: z.boolean(),
  creado_en: z.string().datetime(),
});
export type Producto = z.infer<typeof ProductoSchema>;

export const NuevoProductoSchema = ProductoSchema.omit({
  id: true,
  activo: true,
  creado_en: true,
});
export type NuevoProducto = z.infer<typeof NuevoProductoSchema>;

export const VentaSchema = z.object({
  id: z.string().uuid(),
  fecha: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  producto_id: z.string().uuid(),
  producto_tipo: z.string().min(1),
  producto_color: z.string().min(1),
  cantidad: z.number().int().positive(),
  precio_unitario_centavos: z.number().int().nonnegative(),
  total_centavos: z.number().int().nonnegative(),
  cliente_nombre: z.string().default(""),
  cliente_telefono: z.string().default(""),
  creado_en: z.string().datetime(),
});
export type Venta = z.infer<typeof VentaSchema>;

export const NuevaVentaSchema = z.object({
  producto_id: z.string().uuid(),
  cantidad: z.number().int().positive(),
  cliente_nombre: z.string().default(""),
  cliente_telefono: z.string().default(""),
});
export type NuevaVenta = z.infer<typeof NuevaVentaSchema>;

export const GastoSchema = z.object({
  id: z.string().uuid(),
  fecha: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  categoria: z.enum(CATEGORIAS_GASTO),
  descripcion: z.string().trim().min(1),
  monto_centavos: z.number().int().positive(),
  creado_en: z.string().datetime(),
});
export type Gasto = z.infer<typeof GastoSchema>;

export const NuevoGastoSchema = GastoSchema.omit({ id: true, creado_en: true });
export type NuevoGasto = z.infer<typeof NuevoGastoSchema>;
```

### Migrations
NOT APPLICABLE — no hay migraciones porque no hay base relacional. El "esquema" es la fila de
encabezado de cada pestaña del Sheet (arriba); crearla a mano es parte de la configuración inicial,
documentada en §10 *Accounts to create first*. Si se agrega un campo, `.claude/skills/agregar-
recurso-sheets/SKILL.md` documenta el procedimiento (agregar la columna al final de la pestaña real
y al rango en `google-sheets-repo.ts` en el mismo commit).

### Seed data
`MemoryRepo` arranca con 4 productos de ejemplo (2 gorritos, 2 colitas, distintos colores y stock)
para que la app sea usable apenas se clona — ver el paso 2, archivo `memory-repo.ts`. No hay seed
para `GoogleSheetsRepo`: el Sheet real empieza vacío salvo la fila de encabezado.

## 5. API Design

**Este proyecto no tiene una API REST pública.** Las mutaciones ocurren a través de Next.js Server
Actions (`src/app/**/actions.ts`), llamadas directamente desde los `<form>` — no hay cliente HTTP
propio ni contrato JSON que versionar, porque no hay más consumidor que esta misma app. Esta es una
desviación deliberada del layout genérico de `knowledge/capabilities/api-design.md`: para una
herramienta de 2 usuarias sin consumidores externos, una capa REST completa es superficie que nadie
usa.

Dos *route handlers* existen porque necesitan ser HTTP plano, no una Server Action:

### Conventions
- No hay `/api/v1` — solo los dos endpoints de abajo, cada uno documentado por completo.
- Envelope de error de las Server Actions: `{ ok: false, error: string }`. Envelope de éxito:
  `{ ok: true, data: T }`. Un solo shape, en todo el proyecto — ver `CLAUDE.md` regla de código #6.
- Validación: Zod, esquemas en `src/lib/data/schemas.ts` (§4), aplicada en el primer renglón de
  cada Server Action y de cada route handler.
- Paginación / rate limiting / idempotencia: NOT APPLICABLE — sin consumidores externos, sin
  volumen que lo justifique (ver §16 Cost model).

### Routes

| Method | Path | Description | Auth | Rate limit |
|---|---|---|---|---|
| GET | `/api/health` | Health check — confirma que el server responde | público | ninguno |
| POST | `/api/auth` | Verifica el PIN, firma y setea la cookie de sesión | público (es el propio login) | ninguno — 2 usuarias conocidas, ver §14 |
| DELETE | `/api/auth` | Cierra la sesión (borra la cookie) | sesión válida | ninguno |

### Critical endpoints — full detail

**`GET /api/health`**
- Response 200: `{ "ok": true }`, `Content-Type: application/json`.
- No toca la capa de datos — solo confirma que el proceso Next.js está sirviendo. Es el primer
  endpoint que existe (paso 1) y el que usan el smoke test y Vercel para el health check de deploy.

**`POST /api/auth`**
- Body: `{ "pin": string }`.
- Validación: `z.object({ pin: z.string().min(1) })` — falla → 400, `{ "ok": false, "error": "PIN requerido" }`.
- Compara `sha256(pin)` contra `sha256(process.env.APP_PIN)` con `crypto.timingSafeEqual` (§8) —
  nunca una comparación `===` directa de strings.
- Correcto → firma un JWT (`jose`, HS256, `SESSION_SECRET`), setea cookie `session`
  (`HttpOnly`, `Secure` en producción, `SameSite=Lax`, `Max-Age=2592000` — 30 días), responde 200
  `{ "ok": true }`.
- Incorrecto → responde 401 `{ "ok": false, "error": "PIN incorrecto" }`. No hay bloqueo por
  intentos fallidos en v1 (Non-Goal — 2 usuarias conocidas, no un formulario público; ver §14).

**`DELETE /api/auth`**
- Borra la cookie `session` (`Max-Age=0`), responde 200 `{ "ok": true }`. Sin body.

## 6. Frontend Architecture

### Routes
| Route | Page | Data source | Auth |
|---|---|---|---|
| `/login` | Formulario de PIN | ninguna | público |
| `/` | Dashboard: KPIs + stock bajo | `kpis.ts` sobre `getRepo()` | sesión |
| `/productos` | Listado de productos | `getRepo().listProductos()` | sesión |
| `/productos/nuevo` | Alta de producto | — | sesión |
| `/productos/[id]/editar` | Edición de producto | `getRepo().getProducto(id)` | sesión |
| `/ventas` | Historial de ventas | `getRepo().listVentas()` | sesión |
| `/ventas/nueva` | Registrar venta | `getRepo().listProductos()` (para el selector) | sesión |
| `/ventas/[id]` | Detalle de venta + compartir | `getRepo().getVenta(id)` | sesión |
| `/gastos` | Listado de gastos | `getRepo().listGastos()` | sesión |
| `/gastos/nuevo` | Alta de gasto | — | sesión |
| `/offline` | Fallback sin conexión (PWA) | ninguna | sesión (se muestra igual sin red) |

### Rendering strategy
Todo server-rendered, sin caché (`export const dynamic = "force-dynamic"` en cada página que lee de
`getRepo()`) — con Sheets como fuente de verdad y 2 usuarias que pueden escribir casi al mismo
tiempo, servir una versión cacheada es peor que un request un poco más lento. Formularios usan
Server Actions con `revalidatePath()` sobre la ruta afectada al terminar, así la navegación de
"volver a la lista" siempre muestra el dato recién escrito.

### Component hierarchy
```
app/page.tsx (dashboard, server)
├── <KpiCard /> × 4        (ventas período, inversión, ganancia, stock bajo — server, sin estado)
└── <StockBajoList />      (server)

app/ventas/nueva/page.tsx (server, carga productos)
└── <VentaForm />           (client — selects producto+color, cantidad, cliente; "use client" por
                              el manejo de estado del formulario y validación en vivo)

app/ventas/[id]/page.tsx (server)
└── <CompartirVentaButton /> (client — usa navigator.share / window.open, necesita el browser)
```

### State management
Sin estado global. Cada formulario tiene su propio `useState` local para los campos y errores de
validación en vivo; el estado real vive en el Sheet, no en el cliente. Sin `react-query` ni SWR —
no hay dato que se vuelva a pedir sin una navegación de por medio (rule: no construir lo que nadie
pidió, `knowledge/shapes/internal-tool.md` Pitfalls).

### Loading, empty, and error states
- **Loading:** cada página server usa `loading.tsx` con un esqueleto simple (3 barras grises) —
  Sheets puede tardar más que una base de datos local.
- **Empty:** "Todavía no hay ventas" / "Todavía no hay productos" / "Todavía no hay gastos", con un
  botón directo a la pantalla de alta.

## 8. Authentication & Authorization

### Provider and rationale
PIN único compartido + cookie de sesión firmada (`jose`, JWT HS256) — no hay proveedor externo ni
cuentas individuales. Decisión explícita del usuario tras confirmar el trade-off: sin esto, cualquiera
con el link puede ver y editar ventas/stock.

### Flows
**Login:** `/login` (form, campo PIN numérico) → `POST /api/auth` → PIN correcto → cookie `session`
seteada, redirect a `/`. PIN incorrecto → mensaje "PIN incorrecto", el campo se limpia, foco vuelve
al input.
**Sesión activa:** cada request a una ruta protegida pasa por `middleware.ts`, que verifica la firma
y expiración del JWT en la cookie `session`. Válida → continúa. Inválida/ausente → redirect a
`/login` (páginas) o 401 (rutas `/api/*` que no sean `/api/health` o `/api/auth`).
**Logout:** botón en el layout → `DELETE /api/auth` → cookie borrada → redirect a `/login`.
**Expiración:** a los 30 días la cookie deja de validar; el próximo request redirige a `/login` sin
aviso previo (no hay refresh silencioso — a este uso, volver a tipear el PIN cada mes es aceptable).
**No hay registro.** Ninguna ruta crea una cuenta; el PIN es un valor de entorno que el usuario elige
y puede cambiar en Vercel sin tocar código.

### Route protection
| Surface | Rule | Enforced where |
|---|---|---|
| `/*` excepto `/login` | sesión válida | `src/middleware.ts` |
| `/api/*` excepto `/api/health`, `/api/auth` (POST) | sesión válida | `src/middleware.ts` |
| `/api/health` | público | sin chequeo — intencional |
| `/api/auth` POST | público (es el login) | sin chequeo — intencional |

**Enforcement rule:** la sesión se verifica en `middleware.ts` para *toda* request que matchee su
`matcher`, server-side. No hay chequeo solo-de-UI en ningún lado.

### Roles and permissions
| Role | Can | Cannot |
|---|---|---|
| (único — sesión válida) | Todo: crear/editar productos, registrar ventas, anotar gastos, ver dashboard | Nada distinto — no hay una segunda categoría de acceso en v1 (Non-Goal, §1) |

### Sessions
JWT firmado HS256 con `SESSION_SECRET` (mínimo 32 bytes, ver `.env.example`), payload
`{ ok: true, iat }`, expiración 30 días codificada en el propio JWT (`exp` claim) y en el `Max-Age`
de la cookie. Cookie: `HttpOnly`, `Secure` (solo en producción — `NODE_ENV === "production"`),
`SameSite=Lax`, `Path=/`. CSRF: `SameSite=Lax` más el hecho de que todas las mutaciones son Server
Actions (que Next.js protege con un token de acción propio) cubren el riesgo — no hay un endpoint
JSON de mutación que un sitio de terceros pueda invocar en nombre del usuario.

### Multi-tenancy / row-level isolation
NOT APPLICABLE — un solo Sheet, una sola "cuenta". No hay boundary que cruzar.

### Step 3 — Auth: PIN, sesión, middleware

**Do**

- `src/lib/auth/session.ts`:
  ```typescript
  import { SignJWT, jwtVerify } from "jose";
  import { createHash, timingSafeEqual } from "node:crypto";

  const TREINTA_DIAS_SEG = 60 * 60 * 24 * 30;

  function secretKey(): Uint8Array {
    return new TextEncoder().encode(process.env.SESSION_SECRET);
  }

  export function pinValido(pinIngresado: string): boolean {
    const a = createHash("sha256").update(pinIngresado).digest();
    const b = createHash("sha256").update(process.env.APP_PIN ?? "").digest();
    return timingSafeEqual(a, b);
  }

  export async function firmarSesion(): Promise<string> {
    return new SignJWT({ ok: true })
      .setProtectedHeader({ alg: "HS256" })
      .setIssuedAt()
      .setExpirationTime(`${TREINTA_DIAS_SEG}s`)
      .sign(secretKey());
  }

  export async function sesionValida(token: string | undefined): Promise<boolean> {
    if (!token) return false;
    try {
      await jwtVerify(token, secretKey());
      return true;
    } catch {
      return false;
    }
  }

  export const COOKIE_SESION = "session";
  export const MAX_AGE_COOKIE = TREINTA_DIAS_SEG;
  ```

  ```typescript
  import { cookies } from "next/headers";
  import { z } from "zod";
  import { pinValido, firmarSesion, COOKIE_SESION, MAX_AGE_COOKIE } from "@/lib/auth/session";

  const BodySchema = z.object({ pin: z.string().min(1) });

  export async function POST(request: Request) {
    const parsed = BodySchema.safeParse(await request.json().catch(() => null));
    if (!parsed.success) {
      return Response.json({ ok: false, error: "PIN requerido" }, { status: 400 });
    }
    if (!pinValido(parsed.data.pin)) {
      return Response.json({ ok: false, error: "PIN incorrecto" }, { status: 401 });
    }
    const token = await firmarSesion();
    const store = await cookies();
    store.set(COOKIE_SESION, token, {
      httpOnly: true,
      secure: process.env.NODE_ENV === "production",
      sameSite: "lax",
      path: "/",
      maxAge: MAX_AGE_COOKIE,
    });
    return Response.json({ ok: true });
  }

  export async function DELETE() {
    const store = await cookies();
    store.delete(COOKIE_SESION);
    return Response.json({ ok: true });
  }
  ```

### Step 5 — Registrar venta + descuento de stock

**Do**
Crear:
- `src/lib/data/stock.ts`:
  ```typescript
  import type { DataRepo } from "./repo";

  export type ResultadoStock =
    | { ok: true; nuevoStock: number }
    | { ok: false; error: string };

  const INTENTOS_MAX = 3;
  const espera = (ms: number) => new Promise((r) => setTimeout(r, ms));

  export async function decrementarStock(
    repo: DataRepo,
    productoId: string,
    cantidad: number
  ): Promise<ResultadoStock> {
    for (let intento = 0; intento < INTENTOS_MAX; intento++) {
      const producto = await repo.getProducto(productoId);
      if (!producto || !producto.activo) {
        return { ok: false, error: "producto no encontrado" };
      }
      const nuevoStock = producto.stock_actual - cantidad;
      if (nuevoStock < 0) {
        return { ok: false, error: "stock insuficiente" };
      }
      await repo.updateProducto(productoId, { stock_actual: nuevoStock });
      const verificacion = await repo.getProducto(productoId);
      if (verificacion?.stock_actual === nuevoStock) {
        return { ok: true, nuevoStock };
      }
      await espera(200 * (intento + 1));
    }
    return { ok: false, error: "conflicto de escritura, intenta de nuevo" };
  }
  ```

### Step 7 — Dashboard + historial de ventas

**Do**
Crear:
- `src/lib/data/kpis.ts`:
  ```typescript
  import type { DataRepo } from "./repo";
  import { UMBRAL_STOCK_BAJO } from "./schemas";

  function dentroDe(fechaISO: string, desde: Date): boolean {
    return new Date(`${fechaISO}T00:00:00`) >= desde;
  }
  function inicioDeHoy(): Date {
    const d = new Date();
    d.setHours(0, 0, 0, 0);
    return d;
  }
  function inicioDeSemana(): Date {
    const d = inicioDeHoy();
    d.setDate(d.getDate() - d.getDay());
    return d;
  }
  function inicioDeMes(): Date {
    const d = inicioDeHoy();
    d.setDate(1);
    return d;
  }

  export async function calcularKpis(repo: DataRepo) {
    const [ventas, gastos, productos] = await Promise.all([
      repo.listVentas(),
      repo.listGastos(),
      repo.listProductos(),
    ]);

    const sumaVentas = (desde: Date) =>
      ventas.filter((v) => dentroDe(v.fecha, desde)).reduce((acc, v) => acc + v.total_centavos, 0);
    const sumaGastosMes = gastos
      .filter((g) => dentroDe(g.fecha, inicioDeMes()))
      .reduce((acc, g) => acc + g.monto_centavos, 0);
    const ventasMes = sumaVentas(inicioDeMes());

    return {
      ventasHoyCentavos: sumaVentas(inicioDeHoy()),
      ventasSemanaCentavos: sumaVentas(inicioDeSemana()),
      ventasMesCentavos: ventasMes,
      inversionMesCentavos: sumaGastosMes,
      gananciaMesCentavos: ventasMes - sumaGastosMes,
      stockBajo: productos.filter((p) => p.activo && p.stock_actual <= UMBRAL_STOCK_BAJO),
    };
  }
  ```

## 12. Deployment Strategy

### Hosting
Vercel, plan Hobby (gratis), región por defecto (auto, más cercana al tráfico). Build command:
`pnpm build` (detectado automático por el framework preset de Next.js). Output: manejado por el
adapter de Vercel para Next.js (no hay `output directory` manual que configurar). Runtime: Node.js,
serverless functions para las Server Actions y route handlers.

### Environments
| Environment | Branch | URL | Database | Third-party mode |
|---|---|---|---|---|
| Local | — | localhost:3000 | `SHEETS_MODE=memory` (o `google` contra un Sheet de prueba, a elección) | — |
| Preview | cualquier PR | auto-generada por Vercel | `SHEETS_MODE=google` contra el mismo Sheet real (no hay Sheet de staging — volumen bajo, el riesgo de una escritura de prueba es aceptable y reversible a mano) | credenciales reales |
| Production | `main` | `<proyecto>.vercel.app` (o dominio propio si se agrega) | `SHEETS_MODE=google`, Sheet real | credenciales reales |

### CI/CD
`.github/workflows/ci.yml` (ya en `workspace/`) corre en cada push y PR: install → typecheck → lint
→ format:check → test → build → instala Chromium de Playwright → test:e2e. Las mismas 6 puertas de
§20.1. Vercel despliega automático en cada push a `main` una vez que CI pasa (configurar "Required
status check" en la protección de la rama `main` en GitHub, paso manual del usuario).

### Release and rollback
Cada push a `main` es un deploy. Un deploy roto se revierte desde el dashboard de Vercel
("Promote to Production" sobre el deploy anterior) — instantáneo, sin rebuild. No hay migraciones
que ordenar contra el deploy (§4 Migrations: NOT APPLICABLE).

### Domain, DNS, TLS
El subdominio `*.vercel.app` incluido alcanza para v1 (uso interno, no necesita marca propia). Si
más adelante se agrega un dominio propio, Vercel gestiona el certificado TLS automático — el único
paso manual es apuntar el DNS del dominio a Vercel.

## 13. Testing Strategy

| Layer | Framework | What it covers | Where | Runs |
|---|---|---|---|---|
| Unit | Vitest 4.1.10 | `MemoryRepo`, `decrementarStock`, `calcularKpis`, `pinValido`/`firmarSesion`, `mensajeVenta`/`linkWhatsapp` | `src/lib/**/*.test.ts` | cada commit (CI) |
| E2E | Playwright 1.62.1 | Los 3 flujos que el negocio no puede perder (§13 abajo) | `e2e/*.spec.ts` | cada commit (CI), contra `SHEETS_MODE=memory` |

No hay capa de integración separada: como no hay base de datos relacional ni API REST, los tests
unitarios contra `MemoryRepo` **son** la integración de la capa de datos (la misma interfaz que usa
`GoogleSheetsRepo`), y los E2E cubren la integración de UI + Server Actions + capa de datos junta.

### Critical flows to cover E2E
1. **Login con PIN** — es la puerta de entrada; si se rompe, nadie usa la app.
2. **Registrar una venta y confirmar el descuento de stock** — el flujo que existe para no perder
   plata ni vender de más.
3. **Compartir una venta por WhatsApp** — el pedido explícito del usuario que motivó todo el
   proyecto además del control de stock.

### Test data
`MemoryRepo` se siembra en su constructor (paso 2) — cada test/spec arranca desde el mismo estado
conocido porque cada proceso de test crea su propia instancia (sin estado compartido entre archivos
de test; Vitest y Playwright corren cada archivo en un contexto aislado). No hay base de datos real
que provisionar para tests — es la ventaja directa de tener `MemoryRepo` detrás de la misma interfaz
que `GoogleSheetsRepo` (ver §2, desviación deliberada del ORM/DB genérico).

### What is deliberately not tested
`GoogleSheetsRepo` no tiene test automatizado contra la API real de Google — necesitaría
credenciales reales en CI, que este proyecto no provisiona a este tamaño (sería una cuenta de
servicio de prueba más para mantener). Se verifica a mano una vez por el usuario en el paso 8 y en
producción tras el deploy (paso 14). Es una decisión, no un olvido — ver §20.2 Riesgo #1.

## 14. Security & Secrets

| Concern | Control | Implemented in |
|---|---|---|
| Secret storage | Variables de entorno de Vercel (cifradas en reposo), nunca en el repo | Vercel dashboard, `.env.example` sin valores reales |
| Secret rotation | Cambiar `APP_PIN` o `SESSION_SECRET` en Vercel invalida todas las sesiones activas al instante (las firmadas con el secreto viejo dejan de verificar) | Manual, sin cadencia fija — a criterio de las usuarias |
| Input validation | Zod en cada Server Action y route handler, antes de tocar `DataRepo` | `src/lib/data/schemas.ts`, cada `actions.ts` |
| Output encoding / XSS | React escapa por defecto; cero `dangerouslySetInnerHTML` en todo el proyecto | Todo `src/app/**` y `src/components/**` |
| SQL injection | NOT APPLICABLE — no hay SQL, la única "consulta" es un rango de la API de Sheets | — |
| AuthN / AuthZ | Ver §8 — verificado server-side en `middleware.ts` para toda ruta protegida | `src/middleware.ts` |
| CSRF | `SameSite=Lax` en la cookie de sesión + Server Actions (token de acción propio de Next.js) — sin endpoint JSON de mutación invocable desde otro origen | `src/app/api/auth/route.ts`, Server Actions |
| Rate limiting / abuse | Ninguno en v1 — 2 usuarias conocidas, no un formulario público expuesto a bots. Riesgo aceptado explícitamente, no un olvido | — |
| Webhook verification | NOT APPLICABLE — no hay webhooks entrantes | — |
| Dependency audit | `pnpm audit` — no está en CI en v1 (Non-Goal de mínima superficie), correr manualmente antes de cada release grande | manual |
| Security headers | Next.js 16 aplica un set razonable por defecto; no se agregan headers custom en v1 | default del framework |
| PII handling | `cliente_nombre` y `cliente_telefono` son opcionales, quedan en el Sheet del propio negocio (no se envían a ningún tercero salvo el propio WhatsApp que la usuaria elige abrir) | `Venta` en §4 |
| Logging hygiene | `src/lib/logger.ts` (paso 13) nunca recibe el PIN, el `SESSION_SECRET` ni el contenido de la cookie — solo mensajes y metadata de error | `src/lib/logger.ts` |

**Hard rules**
- Ningún secreto se commitea, se imprime en un log, ni llega al bundle de cliente — `APP_PIN`,
  `SESSION_SECRET` y las credenciales de Google solo se leen en código server-side
  (`src/lib/env.ts`, `src/lib/auth/**`, `src/lib/data/google-sheets-repo.ts`, `sheets-client.ts`),
  nunca en un componente `"use client"`.
- Toda verificación de autorización corre server-side, antes de tocar `DataRepo` — nunca "se oculta
  el botón" como único control.

Este proyecto no maneja datos regulados (salud, financieros, de menores, o de residentes de la UE
en volumen) — es un control de inventario y ventas de un emprendimiento chico. Los únicos datos
personales son nombre/teléfono de cliente, opcionales y bajo el control directo de las dueñas del
negocio.

**Quién autoriza el manifest de paquetes — decisión tomada en generación:** no hay scaffolder.
Ninguna línea de §10 Bootstrap corre `pnpm create next-app` ni equivalente — `package.json` (y el
resto de la lista de arriba) ya viene en `workspace/` y `pnpm install` en Bootstrap instala
directamente desde él. Esto evita depender de las banderas exactas de un generador interactivo
(riesgo documentado en `knowledge/runtime-tracks/ts-node.md`) y es la opción "No — bare greenfield"
de la regla de `questions/phase-4-generate.md` Step 4.

**Resolución de módulos:** un único convenio, `@/*` → `src/*`, declarado en `tsconfig.json`
`compilerOptions.paths` y consistente porque Next.js resuelve alias directamente desde ese mismo
campo — no hay un segundo resolver (Jest, un bundler alternativo) que pueda desalinearse: Vitest lee
la config de Vite/`vite-tsconfig-paths` implícitamente vía su propio `tsconfig.json` resolution en
modo `bundler`... **nota para quien construya:** si `pnpm test` no resuelve `@/`, agregar
`resolve: { alias: { "@": "/src" } }` a `vitest.config.ts` es el único ajuste esperado — no cambiar
el alias en sí.

**Byte-exact artifact reconciliation:** ninguna. No hay golden files ni fixtures que este blueprint
compare byte a byte — todas las aserciones de §9 son sobre propiedades (status codes, presencia de
campos, valores numéricos calculados a partir del propio `MemoryRepo` sembrado), no sobre strings
copiados de una ejecución anterior.

**El bundle dentro del proyecto:** `tsconfig.json`, `.gitignore` y `vitest.config.ts` excluyen
`blueprints/` explícitamente (ver cada archivo arriba) — así el árbol `blueprints/gestion-ventas-
stock/` puede convivir en el repo sin que `tsc`, `eslint` o `vitest` lo recorran.

### 20.2 Risk register

| # | Riesgo | Impacto | Mitigación en este blueprint | Dueño |
|---|---|---|---|---|
| 1 | **Google Sheets como base de datos.** Sin transacciones reales: si las dos socias editan el mismo producto casi al mismo segundo, puede haber una condición de carrera en el stock. | Un stock ligeramente incorrecto en el peor caso — nunca una venta duplicada ni datos corruptos, porque `Venta`/`Gasto` son solo altas (append), nunca ediciones concurrentes | `decrementarStock` (paso 5) hace lectura-escritura-verificación con 3 reintentos y backoff — no es un lock real, pero cubre el caso realista de este volumen (unas pocas ventas por hora, no por segundo) | Revisar si el volumen de ventas simultáneas crece; el Non-Goal de §1 ya marca la migración a una base real como el camino de salida |
| 2 | **Sin rate limiting en el login.** Un PIN de 4 dígitos sin bloqueo por intentos es fuerza-bruteable en teoría. | Acceso no autorizado si alguien ataca activamente el login | Riesgo aceptado explícitamente por el usuario (decisión de auth de §8) — mitigado en la práctica porque la URL no se publicita y el PIN se puede cambiar en cualquier momento sin redeploy | Si la URL se filtra ampliamente, cambiar `APP_PIN` de inmediato invalida todas las sesiones activas |
| 3 | **`GoogleSheetsRepo` no tiene test automatizado contra la API real** (§13). | Un bug en la integración real solo se descubre a mano, en el paso 8 o en producción | El contrato `DataRepo` idéntico entre `MemoryRepo` y `GoogleSheetsRepo`, más el checklist manual del paso 8, acotan la superficie no cubierta a la traducción HTTP en sí, no a la lógica de negocio (que sí está 100% testeada contra `MemoryRepo`) | Revisar si se automatiza con una cuenta de servicio de prueba, si el proyecto crece |
| 4 | **Cuota de la API de Google Sheets** (60 req/min/usuario). | Errores 429 si el uso crece mucho | A este volumen (2 usuarias, unas pocas escrituras por hora) está muy por debajo del límite — ver §16 Cost model | Revisar si se agrega automatización que llame la API en loop |

### 20.3 Decision log

| # | Decisión | Alternativa descartada | Razón |
|---|---|---|---|
| 1 | Google Sheets como única base de datos | Postgres/Supabase (el default de este framework) | Pedido explícito del usuario — mantener todo visible/editable en la planilla, sin duplicar información |
| 2 | PIN compartido + cookie firmada, sin cuentas individuales | Google Sign-In individual (propuesta inicial de The Architect) | El usuario pidió explícitamente sacar el login basado en cuentas; eligió un PIN compartido (`2026`) tras confirmar el riesgo de dejar la app sin ninguna protección |
| 3 | Server Actions en vez de una API REST | Rutas `/api/v1/*` con un cliente HTTP propio | Sin consumidores externos, una capa REST completa es superficie sin uso — `knowledge/shapes/internal-tool.md` Pitfalls, "over-designing" |
| 4 | `DataRepo` con `MemoryRepo` + `GoogleSheetsRepo` en vez de una sola implementación | Solo `GoogleSheetsRepo`, sin fake | Permite desarrollar, testear (unit + E2E) y probar la app sin credenciales de Google desde el primer minuto, y aísla el riesgo #3 del registro de riesgos a una sola capa delgada |
| 5 | Compartir por `wa.me` / Web Share API, no la API de WhatsApp Business | API de WhatsApp Business (Meta) | Requiere aprobación de Meta y tiene costo por mensaje — innecesario para "abrir un chat con el mensaje ya escrito" |
| 6 | Sin scaffolder (`create-next-app`) — el manifest y configs vienen en `workspace/` | Bootstrap corre `pnpm create next-app` y edita el resultado | Evita depender de flags exactos de un CLI interactivo; control total y reproducible sobre el árbol inicial |
| 7 | Bundle mode (no single-file) | Single file | 14 pasos ≥ 12 — el umbral de `questions/phase-4-generate.md` Step 2, sin preferencia explícita del usuario que lo anule |
| 8 | TypeScript 6.0.3, no 7.0.2 | Pinnear el dist-tag `latest` (7.0.2) | Verificado con una instalación real: `@typescript-eslint` (que `eslint-config-next` trae) exige `typescript <6.1.0` como peer — con 7.0.2 el lint queda con peers rotos. Descubierto en el smoke test de generación, no en el runtime track (que ya lo advertía, pero de forma menos concreta) |
| 9 | ESLint 9.39.5, no 10.8.0 | Pinnear el dist-tag `latest` (10.8.0) | Verificado con una corrida real de `eslint .`: `eslint-config-next@16.3.0` tira `TypeError: scopeManager.addGlobals is not a function` contra ESLint 10.8.0, pese a declarar `eslint: ">=9.0.0"` como peer — el rango declarado no capturó una ruptura interna real |
| 10 | googleapis 174.0.0, no 174.0.1 | Pinnear el dist-tag `latest` (174.0.1) | Verificado con una instalación real: pnpm 11.20 rechaza por política de cadena de suministro cualquier versión publicada en las últimas ~24-48h; 174.0.1 caía justo dentro de esa ventana el día de la generación |
| 11 | `next build --webpack` en vez de `next build` a secas | Dejar Turbopack (el default de Next 16) | Verificado con un build real: `@ducanh2912/next-pwa` depende de webpack (`peerDependencies: {webpack: ">=5.9.0"}`) y Next 16 rechaza el build si detecta una config de webpack bajo Turbopack sin una config de `turbopack` explícita |
| 12 | `pnpm-workspace.yaml` con `allowBuilds` en vez de `pnpm approve-builds` interactivo | Dejar que el builder responda el prompt a mano | Un build headless no puede responder un prompt interactivo — verificado que sin este archivo, `pnpm install` se detiene con `ERR_PNPM_IGNORED_BUILDS` |
